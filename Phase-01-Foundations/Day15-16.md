## What I Learned

### Attack Surface Minimisation

The attack surface represents the different ways an attacker could interact with or attack a system.

Reducing unnecessary services, applications, ports, and functionality reduces the possible attack surface.

Example:

    Unused server
        ↓
    Disable unnecessary services
        ↓
    Fewer exposed services
        ↓
    Smaller attack surface

A practical example from the room was turning off an insecure, non-critical server.

The relevant principle was:

    Attack Surface Minimisation

### Least Privilege

Users and systems should only receive the permissions they actually need.

Example:

    Sales employee
        ↓
    Needs product information
        ↓
    Give access only to products/prices
        ↓
    Do not give unnecessary administrative access

This limits the potential damage if an account is compromised.

### Defence in Depth

Security should not depend on a single security mechanism.

Instead, multiple layers should protect the system.

Example:

    Firewall
       ↓
    Network segmentation
       ↓
    Authentication
       ↓
    Authorization
       ↓
    Endpoint protection
       ↓
    Logging / Monitoring

If one layer fails, other layers can still provide protection.

### Failing Securely

When something goes wrong, a system should fail in a secure state rather than exposing sensitive information or granting additional access.

Security failures should not create new opportunities for attackers.

### Preparing for Error and Exception Handling

Systems should be designed to handle unexpected situations safely.

For example, an ATM should be able to deal with unexpected:

- Network failures
- Power failures
- Invalid input
- Hardware problems

The security principle associated with this example was:

    Preparing for Error and Exception Handling

### Separation of Duties

Important actions should not necessarily be controlled by a single person.

Separating responsibilities can prevent one individual from having excessive control.

For example:

    Employee A
        ↓
    Requests payment

    Employee B
        ↓
    Approves payment

### Complete Mediation

Access should be checked whenever a protected resource is accessed.

A system should not assume that a user who was previously authorized is automatically authorized forever.

### Security Economy

Security mechanisms should be practical and efficient.

Security should provide appropriate protection without introducing unnecessary complexity or cost.

### Psychological Acceptability

Security mechanisms should be usable.

If security controls are excessively difficult or inconvenient, users may attempt to bypass them.

Good security should therefore consider both security and usability.

## Plaintext and Ciphertext

Plaintext is the original readable information.

Ciphertext is the transformed information produced after encryption.

    Plaintext
        ↓
    Encryption + Key
        ↓
    Ciphertext

To recover the original information:

    Ciphertext
        ↓
    Decryption + Key
        ↓
    Plaintext

## Encryption

Encryption transforms readable information into a form that should not be understandable without the required key.

The basic model is:

    Plaintext
        +
    Encryption Algorithm
        +
    Key
        ↓
    Ciphertext

## Symmetric Encryption

Symmetric encryption uses the same secret key for encryption and decryption.

    Same Secret Key
          ↓
    Plaintext → Encryption → Ciphertext
                              ↓
                           Decryption
                              ↓
                           Plaintext

The main challenge is securely sharing the secret key between communicating parties.

## Asymmetric Encryption

Asymmetric cryptography uses a key pair:

    Public Key
    Private Key

The keys are mathematically related but serve different purposes.

A simplified encryption example is:

    Sender
      ↓
    Encrypt with recipient's Public Key
      ↓
    Ciphertext
      ↓
    Recipient
      ↓
    Decrypt with Private Key
      ↓
    Original Message

The private key should remain secret.

## Caesar Cipher

The Caesar cipher is a simple substitution cipher where letters are shifted by a chosen number of positions.

For example, with a shift of 3:

    A → D
    B → E
    C → F

The shift is not universally fixed.

A Caesar cipher can use different shift values, so the key must be determined or brute-forced.

For example:

    Shift 1
    Shift 2
    Shift 3
    ...
    Shift 25

Because there are only 25 useful non-zero shifts in the English alphabet, Caesar ciphers can easily be brute-forced.

## Hashing

Hashing is different from encryption.

A hash function transforms input into a fixed-size output.

    Password
        ↓
    Hash Function
        ↓
    Hash

The important difference is:

    Encryption
    → Designed to be decrypted with a key

    Hashing
    → Designed as a one-way transformation

This distinction became especially important in the next room, Crack the Hash.

## Hash Cracking Process

         ↓
    Identify Hash Type
         ↓
    Choose Hashcat Mode
         ↓
    Choose Attack Method
         ↓
    Choose Wordlist
         ↓

         ↓
    Find Matching Candidate
         ↓
    Recover Password

The important lesson was that the cracking process depends heavily on correctly identifying the hash type.

## Hashcat

Hashcat is a password recovery and hash-cracking tool.

The general syntax is:

    hashcat -m <mode> <hash-file> <wordlist>

For example:

    hashcat -m 0 hash.txt rockyou.txt

The -m option specifies the hash mode.

## Hashcat Modes

Some of the modes relevant to Crack the Hash were:

    0       MD5
    100     SHA-1
    900     MD4
    1000    NTLM
    1400    SHA-256
    160     HMAC-SHA1
    1800    SHA-512 Crypt
    3200    bcrypt

Choosing the correct mode is necessary for Hashcat to process the hash correctly.

## RockYou Wordlist

I used the RockYou password wordlist as the main dictionary.

A wordlist contains potential passwords that can be tested against a target hash.

The basic attack looks like:

    Target Hash
         ↓
    Candidate from RockYou
         ↓
    Hash Candidate
         ↓
    Compare
         ↓
    Match?

If a candidate produces the same hash as the target, the password has been recovered.

## Filtering the Wordlist

The bcrypt challenge was significantly slower because bcrypt is designed to be computationally expensive.

The room hint suggested reducing the search space by looking at four-character words.

I created a smaller wordlist using:

    grep -E '^[a-zA-Z]{4}$' ~/Desktop/rockyou.txt > ~/Desktop/rockyou4.txt

I then checked the number of entries with:

    wc -l ~/Desktop/rockyou4.txt

The filtered wordlist contained approximately:

    9786 entries

This demonstrated how reducing the search space can make a difficult cracking problem much more manageable.

## Bcrypt

The bcrypt hash used in the challenge had the form:

    $2y$12$...

The corresponding Hashcat mode is:

    3200

Bcrypt was considerably slower to crack than algorithms such as MD5 or SHA-1.

This is intentional.

Password hashing algorithms such as bcrypt are designed to make large-scale password guessing more expensive.

The recovered password was:

    bleh

## Hashcat Potfile

Hashcat can store previously cracked hashes in its potfile.

Therefore, running an attack again can sometimes result in:

    All hashes found as potfile and/or empty entries!

Instead of running the attack again, the stored result can be displayed using:

    hashcat -m <mode> <hash-file> --show

This was an important practical lesson because a previous cracking result may already be stored even when a new attack appears to do nothing.

## MD4

One of the challenges used an MD4 hash:

    279412f945939ba78ce0758d3fd83daa

The corresponding Hashcat mode is:

    900

The recovered password was:

    Eternity22

This demonstrated that simply running a basic wordlist attack does not always guarantee a result.

The candidate password format and attack strategy also matter.

## Key Takeaways

### Security Principles

- Security should be designed into systems rather than added as an afterthought.
- Least privilege limits unnecessary access.
- Attack surface minimisation reduces possible attack paths.
- Defence in depth provides multiple security layers.
- Systems should fail securely.
- Security controls need to consider usability.
- Error and exception handling is also a security concern.

### Cryptography

- Encryption and hashing are different concepts.
- Symmetric encryption uses a shared secret key.
- Asymmetric cryptography uses public and private keys.
- Caesar cipher uses a configurable shift rather than one universal shift.
- Hashing is designed as a one-way transformation.

### Hash Cracking

- Correct hash identification is essential.
- Hashcat uses different modes for different algorithms.
- Dictionary attacks can be effective against weak/common passwords.
- Wordlist filtering can reduce the search space.
- Slow password hashing algorithms such as bcrypt make brute-force attacks significantly more expensive.
- Hashcat's potfile can preserve previous cracking results.
- `--show` can retrieve previously cracked passwords.
